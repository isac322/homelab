# 리뷰 차원 체크리스트

SKILL.md의 PRR-08–PRR-23과 PRR-38–PRR-56이 가리키는 세부 항목이다. 해당 없는 차원은 건너뛰되, 건너뛴 이유를 코멘트의 `Not verified`에 한 줄로 남긴다. 트리거된 렌즈(§10)는 건너뛰지 않는다.

## 1. 실제로 문제를 해결하는가

1. PR 설명, 커밋 메시지, 연결 이슈에서 주장을 뽑아 원자적 claim으로 쪼갠다. 서로 다른 코드 경로·계약·메커니즘을 건드리는 claim은 따로 판정한다.
2. 각 claim에 기대 계약(문서, 공개 API, 기존 테스트, upstream 명세)을 적는다. 계약이 없으면 결함인지부터 판단한다(`issue-validation`).
3. 세 기준점에서 같은 재현을 돌린다(PR 코드 실행은 §14 채널에서만).
   - merge-base(PR 적용 전): 주장된 실패가 재현돼야 한다.
   - 현재 main: 이미 고쳐졌는지 본다. 커밋이 다른 PR을 통해 간접 머지됐는지, 다른 PR에 흡수됐는지, 배포된 옛 이미지나 릴리스와 main이 어떻게 다른지도 본다. 고쳐졌으면 `references/stale-pr-audit.md`로 간다.
   - PR head. head가 오래됐으면 main 위로 rebase한 scratch 사본: 통과해야 한다.
   - 정상 대조군(healthy control): 재현 환경이 정상 동작을 표현할 수 있는지 보인다.
4. 수정 위치가 근본 원인과 맞는지 본다. 원인 체인이 없으면 `five-whys-root-cause-analysis`로 도출하고, 여기서는 원인과 수정 위치의 일치만 판정한다.
5. 수정이 올바른 계층에 들어갔는지 대안과 비교해 근거로 평가한다(호출자 쪽 vs 근본 쪽, 통제된 거부 vs 재구현). 선호로 판정하지 않는다.
6. 버전 게이트나 조건식을 고치는 PR이면 결함을 도입한 커밋과 그것을 포함한 릴리스를 upstream 소스로 확인하고, 조건식이 결함 조건과 경계값을 정확히 덮는지 본다.
7. 증상 패치 신호: 타임아웃 증가, 재시도 추가, skip, assertion 완화, 오류 무시. 근본 수정 없이 이것만 있으면 P1이다.

## 2. 영향 범위 (blast radius)

- 변경된 심볼의 호출자와 소비자 전체(같은 status/계약을 읽는 형제 컴포넌트 포함).
- 열린 형제 PR과 겹치는 파일·경로, main과의 충돌 상태.
- 해결되지 않은 리뷰 스레드.
- 업그레이드 경로: 직전 릴리스 상태에서 이 버전으로 올라올 때 깨지는 것.
- 문서, 예제, 설정 키, 환경 변수 소비자.
- 공개 API, 스키마, CLI 플래그처럼 외부 사용자가 의존하는 표면. 변경이 있으면 전역 `public-api` 규칙을 참조한다.

## 3. 회귀

- 변경된 함수의 모든 호출자와 모든 종료 경로(정상, 오류, 취소, 재시도, 정리)를 끝까지 따라간다.
- 생명주기 전이, finalizer·cleanup, 캐시 무효화, 동시성(경합, 순서 의존)을 본다. 체크리스트는 §10 concurrency/lifecycle.
- 수정이 같은 결함을 다른 경로로 다시 들여오지 않았는지 본다(예: 새로 추가한 정리 블록에 기존 가드가 빠짐).
- 소비자에게 보이는 의도치 않은 부작용은 기존 소스로 입증할 수 있을 때만 must-fix(P1)로 올린다.

## 4. 성능

- 지연, 외부 API 호출량, steady-state에서 캐시 없이 반복되는 호출, 무한 requeue나 재시도 폭주, 불필요한 전체 목록 조회.
- 메모리, 파일 핸들, 스레드·태스크 누수.
- 측정값과 추정값을 구분해 적는다. 근거 없는 수치, 서로 모순되는 수치는 지적한다.

## 5. 보안 패스

별도 패스로 돈다. 해당되는 항목만 확인하고 결과를 `Verified`/`Not verified`에 나눠 적는다.

- 비밀 노출: 로그, status 필드, 아티팩트, 에러 메시지, CI 출력에 토큰·키·자격 정보가 찍히는가. 노출은 규모와 상관없이 blocking이다.
- 인가 순서: 모든 외부 쓰기 전에 인가와 소유권 확인이 끝나는가(fail-closed). 실패 시 열린 상태로 남지 않는가.
- 소유권: 외부 객체를 덮어쓰거나 채택(adopt)할 때 소유 증거를 확인하는가.
- 신뢰 경계: 신뢰할 수 없는 입력이 특권 쓰기에 닿는가(confused deputy, TOCTOU, 네임스페이스·테넌트 경계 넘기, 이스케이프 없는 명령·스크립트 조립).
- 토큰·요청 위조: 서명 검증, audience/issuer 확인, SSRF 가능한 URL 입력.
- CI 워크플로: `${{ github.event.* }}`를 셸에 직접 넣는 인젝션, 과도한 `permissions`, fork PR에서 비밀 접근.
- 공급망: 고정되지 않은 액션(`@main`, `@latest`), 서명·체크섬 없는 다운로드, 새 의존성의 출처.
- 삭제: 가드 없는 prefix 삭제, 범위가 불명확한 정리.
- 보안 정책 우회: SELinux·AppArmor·seccomp·샌드박스·권한·confinement를 우회하는가. 정상 중개·격리 경로가 거부됐을 때 다른 경로로 같은 구성 요소에 닿는 fallback(예: 거부된 bus activation 대신 데몬 바이너리를 직접 실행)도 우회다. 우회는 결함 판정이 아니라 메인테이너 결정 항목이다(SKILL.md PRR-47).

PR이 들여온 취약점(기본 브랜치에도, 최신 공개 릴리스와 릴리스 브랜치에도 없는 것)은 위치, 메커니즘, 수정안을 리뷰에 적고 blocking으로 낸다(PRR-48 [U]). 판정 전에 기본 브랜치 tip, GitHub의 최신 공개 릴리스가 가리키는 태그, 존재하는 릴리스 브랜치 tip들에서 같은 코드 경로를 확인한다. 최신 릴리스는 `gh api repos/<owner>/<repo>/releases/latest`로 확인하고 해당 태그를 fetch한다. `git describe`의 가장 가까운 태그를 최신 릴리스로 간주하지 않는다. 릴리스 정보나 필요한 ref를 확인하지 못했으면 PR 도입으로 단정하거나 공개 세부를 쓰지 않고 PRR-19의 비공개 경로를 따른다. 비밀 값과 바로 쓸 수 있는 익스플로잇 입력은 이 경우에도 인용하지 않는다.

공개 저장소에서 이 PR이 들여오지 않은(기본 브랜치나 릴리스에 이미 있는) 악용 가능한 취약점이나 유출된 비밀을 찾으면(PRR-19, 바꿀 수 있는 기본값):

- 결과의 어떤 필드(ReviewResult.body, comments, thread_replies, summary, blockers, open_items)에도 값, 익스플로잇 경로, 재현 입력을 쓰지 않는다. 결과는 게시될 수 있다. `Considered`에도 적지 않는다.
- 비공개 보고 경로(보안 권고, 메인테이너 연락)는 메인테이너가 정한다. ReviewResult.body에는 세부 없는 문구와 경로를 정해 달라는 요청만 적고, 실제로 하지 않은 보고를 했다고 쓰지 않는다. 문구는 `references/comment-template.md`.
- 유출된 비밀 값은 어디에도 인용하지 않는다(전역 `guardrails`).

## 6. 구조·비례성

- diff 크기가 문제에 비례하는가. 큰 diff면 파일별로 무엇이 왜 바뀌었는지 설명할 수 있어야 한다(실수로 들어온 파일 사본, 전체 의존성 업그레이드, 무관한 리팩터링).
- 근본 수정에 구조 변경이 필요한데 국소 패치로 우회했다면 그 사실을 지적한다. 구조 변경 자체의 결정은 사용자(메인테이너) 몫이다(`isac-decision-brief` 형식으로 ReviewResult.body에 적는다). 머지가 그 결정에 달렸으면 결정 항목이다(PRR-47).
- 반대로 문제보다 과한 추상화·새 계층은 non-blocking으로 지적한다.

## 7. 기타 차원 (해당될 때)

- **테스트 방어력**: 새·변경 테스트가 계약을 실제로 방어하는가. 옛 코드에서 올바른 이유로 실패하고 새 코드에서 통과하는가. 결정적인가. 전체 스위트에서 안전한가. stub이나 mock이 결과를 되돌려주기만 하지 않는가. 수정을 되돌려도 통과하는 테스트는 결함으로 보고한다. 체크리스트는 §10 test audit(PRR-46).
- **의미 보존**: 기존 계약과 검증 항목이 사라지거나 약해지지 않았는가. blocked였던 것이 pass로 재분류되거나, live 전용 claim이 사라지거나, assertion이 약해지거나, 타임아웃만 늘었다면 결함이다.
- **생성물·공개 계약·게이트 코드**: 생성 파일 재생성 누락(CRD, RBAC, 차트 등), 템플릿 도구 간 불일치, values 키와 플래그의 실제 연결, 문서와 샘플의 정확성, 라이선스 표기. diff가 바꾼 워크플로·스크립트에서 실패할 수 없는 게이트(`|| true`, `continue-on-error`, `tee`가 pipefail을 가리는 경우), 남은 TODO·stub. 이것은 게이트 코드의 리뷰이고, CI 실행 결과를 근거로 쓰는 것이 아니다(PRR-38).
- **도메인 불변조건**: 프로젝트가 불변조건을 명시했으면(예: fail-closed, 소유권·인가 순서, 관찰 전용 모드는 쓰기 없음, 단일 writer) 그 목록으로 확인한다. 목록은 프로젝트 문서가 소유한다.
- **의존성·보안 업데이트 PR**: 현재 advisory(OSV 등)가 목표 버전에도 남아 있는지, 버전 범위와 lock 정합성, CI 액션 버전, main에서 이미 올렸는지.
- **결정적 vs 일시적 실패**: 리뷰어가 직접 돌린 실행의 실패가 결정적인지(다시 돌려도 같음) 일시적인지(네트워크, 다운로드, 도구) 구분한다. 도구 문제로 실패한 probe는 반박도 확인도 아니다(§12). CI 실패·통과는 판정 근거가 아니다(PRR-38). blocker, 안전 차이, 마이그레이션에서만 생기는 우려를 서로 구분한다.
- **최소 런타임과 요청 vs 관찰 상태**: 언어·라이브러리 기능은 프로젝트가 선언한 최소 런타임·플랫폼(`requires-python`, `engines`, MSRV)에서 판단한다(예: 최소 Python에서 annotation 평가, 표준 라이브러리 API 존재). 비동기 부작용 API는 요청한 값과 관찰한 값을 구분해 보고해야 한다. 관찰하지 않은 성공 문구("Geometry set")는 finding이다(PRR-42).
- **억제 주석**: 새 타입 오류 억제는 테스트 포함 finding(P3, 실제 API·타입 결함을 가리면 P2), 타입이 맞는 수정안과 함께. lint 억제는 프로젝트 관례가 금지할 때만(PRR-45).
- **릴리스 노트·공개 문서 PR**: 노트의 claim마다 구현과 라인 증거로 대조한다. 필수 업그레이드·롤백 경고가 빠졌는지, 보안이나 복구에 대한 과장된 확실성이 있는지 본다.

## 8. 심각도 보정

척도 정의(P0–P3)는 `isac-multi-agent-consensus`가 소유한다. 여기서는 PR 리뷰에서 등급을 매기는 방법과 이 자동화의 PR 리뷰에서 blocking 기준을 다룬다.

- 확인된 결함은 실제 영향으로 매긴다: 몇 명의 사용자, 몇 개의 리소스, 어떤 경로가 영향을 받는지 입증된 범위로 적는다. 예: "5 of 6 hostnames stop routing".
- blocking 기준: P0/P1, 그리고 PR이 들여온 P2 정확성·보안 결함에 증거(재현, 또는 정확한 줄을 인용한 코드 경로 논증)가 있으면 blocking이다 → `BLOCKING`(`REQUEST_CHANGES`). P3는 non-blocking이다.
- 확인도 반박도 안 된 후보는 가장 그럴듯한 최악 결과로 등급을 매긴다(가능성이 아니라 결과). blocking finding이 아니라 open concern이며 SKILL.md PRR-49, PRR-56대로 처리한다(P0–P2 → `OPEN`; 구현 봇 PR에서는 남은 결정 항목이 없을 때 "prove or fix" `BLOCKING`; P3 → 질문). COMMENT를 피하려고 미반박 의심을 낮춰 매기지 않는다. 후보는 `file:line`, 메커니즘, 구체적 트리거가 있어야 한다. 그보다 모호한 의심은 후보가 아니다.
- 결정 항목·메인테이너 hold(PRR-47)가 남으면 확인된 blocking finding이 있어도 이벤트는 `OPEN`이다. PRR-48 [U]의 확인된 PR 도입 취약점만 예외로 `BLOCKING`이다(PRR-56).
- 이 기준은 확인된 결함에만 쓰고, 미반박 의심(PRR-49)의 등급을 낮추지 않는다. 이 기준 자체로 의심을 확인된 결함으로 바꾸지도 않는다. P0/P1에는 현실적인 트리거가 필요하다: 정상 사용에서 닿을 수 있는 코드 경로나 인터리빙이어야 하고, 실제 API가 낼 수 있는 실패를 재현한 fault injection도 현실적 트리거다. 트리거가 정상 사용의 외부 API나 서비스를 통해 현실적으로 닿으면 등급을 내리지 않는다. "실제 입력을 아직 찾지 못했다"는 등급을 내리는 이유가 못 된다. 원자적 API가 없는 외부 상태의 본질적 경합(어떤 수정 후에도 창이 남는 경우)은 최대 P2이고, 계약이 그 경합을 다루지 않으면 P3 질문이다.
- 비밀 유출은 영향 규모와 상관없이 blocking이다.
- 주장한 문제를 해결하지 못하거나 일부만 해결하면서 전체 해결로 설명하는 PR은 P1이다.
- 제품 결함 없이 테스트만 방어하지 못하는 결함(수정 없이도 통과하는 테스트 등)은 보통 P2이고, 정확성 결함이 아니므로 non-blocking이다. 그 테스트가 PR이 들여온 실제 결함을 가리면 그 결함으로 매긴다.
- 실제 API·타입 결함을 가리는 타입 억제(P2)는 가려진 결함이 정확성 결함일 때 blocking이다.
- 이 PR이 들여오지 않은 기존 결함은 등급을 매기지 않고 관찰 사항으로 적는다.

## 9. 증거 규율

- finding마다 `file:line`(또는 `file:symbol`, 아티팩트 위치), 메커니즘, 최소 수정안.
- 1차 소스로 확인한다. 이전 보고, 문서, 작성자 설명은 출발점일 뿐 증거가 아니다.
- 실행한 것, 소스만 읽고 추론한 것, 측정하지 않은 것을 구분한다. 게시 문구는 실제 실행 범위와 정확히 일치해야 한다(main에서만 돌렸으면 "confirmed on both"라고 쓰지 않는다). 끝나지 않은 명령이나 probe, 죽은 실행이나 이전 턴의 출력은 인용하지 않는다(PRR-41, PRR-53).
- CI·check 상태는 증거가 아니다. 리뷰어가 돌린 것만 자기 증거로 적는다(PRR-38).
- 시그널, I/O 블로킹, 타이밍에 대한 런타임 claim과 "결함 없음" 결론은 probe나 challenger를 통과한 논증이 필요하다. 읽기만으로는 부족하다(PRR-49, PRR-51).
- 증거끼리 모순되면 덮지 말고 해소하거나, 해소하지 못했다고 쓴다.
- 확인했고 문제없던 영역도 적는다. 커버리지의 증거다.
- 설계 결정은 현상 유지 편향 없이 비교한다. 근거 없는 강도 표현을 쓰지 않는다.

## 10. 렌즈 체크리스트

트리거가 diff에 있으면 렌즈는 필수다(PRR-43). 본문 `Lenses`에 `- <lens> — <trigger file:line and what> — covered | uncovered: <items>`로 적는다. 렌즈는 서브 리뷰어로 돌리고, 각자 §14 채널에서 probe를 실행할 수 있다. 렌즈 결과가 오지 않았거나 항목이 덮이지 않았으면 같은 턴에서 한 번 다시 돌리고, 그래도 남으면 `OPEN`이다(PRR-53). 도구가 실패했어도 §12 논증으로 항목을 덮었으면 그 렌즈는 덮인 것이다. 체크리스트 항목마다 근거(`file:line`과 probe 또는 §12 논증)를 둔다. "소스로 확인했다" 같은 일괄 주장은 그 항목을 덮지 못한다. `Lenses` 줄에는 덮은 범위만 적는다. 이상 동작을 관찰했으면 그것은 finding이거나 `Considered` 후보이고, coverage 텍스트에 남겨 두지 않는다. 메인 에이전트는 항목별 근거가 없는 렌즈 답을 받아들이지 않고 그 렌즈를 한 번 다시 돌린다(PRR-53). 그래도 근거가 없으면 그 항목은 덮이지 않은 것이고, 이벤트는 `COMMENT`이며 그 렌즈를 `open_items`에 적는다.

- **concurrency/lifecycle** (락, 스레드, async, 시그널, 서브프로세스, 정리). 락을 잡거나, 프로세스·스레드를 만들거나 거두거나, 시그널을 다루거나, close/shutdown 상태를 가진 변경 모듈(파일·패키지)이 둘 이상이면 이 렌즈는 반드시 그런 모듈마다 서브 에이전트 하나로 나눈다(동시 최대 2개, 나머지 순차, PRR-43). 각 서브 에이전트는 자기 모듈에서 아래 항목마다, 특히 락 틈과 close/shutdown 후 사용 항목에 `file:line` 근거를 낸다:
  - 블로킹 I/O(D-Bus, HTTP, 서브프로세스 대기, 파일 잠금)를 감싸고 잡은 락·임계 구역. 그 안의 모든 호출에 타임아웃이 있는가, 연결·인증·이름 조회·introspection 같은 setup 단계의 기본 타임아웃까지 포함해 얼마인가.
  - 기록과 실행의 순서: 되돌려야 할 상태를 기록하기 전에 바꾸지 않는가. 실행 후 응답이 사라지거나 중간에 취소되면 무엇이 남는가.
  - 자원을 얻은 순간과 정리 대상으로 등록한 순간 사이의 창. 그 사이의 시그널, 예외, 취소에서 자원이 새는가.
  - 이름 예약과 정리 소유권: 존재 검사 뒤에 생성하는 이름(파일, 디렉터리, 소켓, 락 파일, 임시 경로)은 배타적 생성(`O_EXCL`, `mkstemp`, `link`)으로만 안전하다. 그렇지 않다면 닿는 모든 디렉터리가 프로세스 전용임을 보인다. 한 프로세스 안의 직렬화(단일 워커, 락)는 이 경합을 반박하지 못한다: 공개 함수의 기본 경로(`/tmp` 등)는 다른 프로세스, CLI, 라이브러리 호출자와 공유된다. 실패 시 정리는 이 호출이 배타적으로 만든 것만 지운다.
  - 락 틈: 변경이 락·임계 구역을 놓았다가 다시 잡거나 같은 상태에 다시 쓰는 지점을 모두 나열한다(그 틈의 sleep·wait·grace period, TERM→wait→KILL 같은 여러 단계 escalation 포함). 틈마다 같은 락을 잡는 다른 행위자가 할 수 있는 일(reap, 등록, 해제, 삭제, 닫기)과 뒤 단계가 무엇을 가정하는지 하나씩 적는다.
  - close/shutdown 후 사용: 변경이 닿는 닫힘·종료 중 상태를 가진 객체·레지스트리마다, `close()` 이후나 그와 경쟁해 부르는 변경·등록 메서드를 모두 확인한다. 그 호출은 거부되거나 그 효과가 종료 경로에서 정리돼야 한다. close()가 찍은 스냅샷은 그 뒤의 등록을 덮지 못한다.
  - 시그널·취소 창: 비동기로 예외를 던지는 핸들러(시그널 핸들러, 콜백, 취소)는 그 예외가 나타날 수 있는 프레임을 모두 적는다: 이벤트 루프가 대기 중일 때, 태스크 그룹·nursery 안의 태스크가 실행 중일 때, 워커 스레드가 일하는 중일 때, 정리(`finally`) 중일 때. 프레임마다 바깥의 `except`가 프레임워크가 감싼 형태(ExceptionGroup/BaseExceptionGroup, 취소 예외 변환)까지 잡는지 확인한다. 비동기 예외를 감싸거나 다른 경로로 보내는 모든 프레임워크가 대상이다(Go의 goroutine panic, Rust의 task panic·취소 같은 대응물 포함). probe는 루프가 대기 중일 때만이 아니라 태스크 한 단계가 실행되는 중에도 시그널을 보낸다. PR 코드를 실행하는 시그널 probe는 §14 격리 채널(PRR-55)로만 돌린다. 종료 중 새 작업 수락, 정리 후 등록도 본다.
  - 정리: 모든 종료 경로에서 정리가 도는가, 정리 중 오류가 나머지 정리와 강제 종료를 막지 않는가, escalation(SIGTERM → SIGKILL)이 건너뛰어지지 않는가.
  - 수정 커밋 hazard 패스(PRR-54): 위 항목을 수정 커밋과 우리가 제안한 수정에 다시 적용한다.
- **input** (새·변경 파라미터, 플래그, 스키마, 설정 키): §11.
- **injection** (다른 언어·형식에 이어 붙이는 문자열): §11.
- **math** (좌표, 크기, 단위, 시간 산술):
  - 픽셀·샘플 중심과 모서리(`(x + 0.5) * W / w - 0.5` 대 `x * W / w`), 반올림 방향, 정수 나눗셈.
  - 경계 원소(첫·마지막 픽셀, 0과 최대값), 빈 범위.
  - 유효 영역과 무효 영역의 경계(마스크, 덮이지 않은 영역, 부분 캡처): 필터·리샘플링이 무효 영역 값을 끌어오는가, 문서가 말하는 무효 영역 표현과 맞는가.
  - 왕복 검산: 변환 → 역변환이 원래 값으로 돌아오는가를 경계값과 비정수 배율에서 실제로 계산한다.
  - 단위 혼동(논리 px 대 물리 px, ms 대 s), overflow, non-finite.
- **test audit** (변경된 테스트, PRR-46): 주장한 동작을 단언하는가, 수정 없이 실패하는가, 고정 sleep, 순서와 무관하게 참인 단언, 우연한 텍스트에 대한 단언, 새 타입 억제(PRR-45).
- **correctness** (항상): §1–§3, PR claim(PRR-51), 최소 런타임과 요청 vs 관찰 상태(§7).
- **docs/convention** (항상): §13.

## 11. 입력 경로와 인젝션

1. 새·변경 파라미터마다 들어오는 경로를 표로 적는다: API·도구 스키마, CLI argv, CLI raw JSON·key=value, 설정 파일, 환경 변수. 스키마 검증을 건너뛰는 경로(JSON 직접 입력, 내부 호출)를 표시한다. 검증이 한 경로에만 있으면 다른 경로의 결함이다.
2. 경로마다 적대적 값을 probe한다: `NaN`/`Infinity`/`10**400`, 아주 큰 값, 음수, 0, int로 쓰인 bool(`true`), 문자열·실수 같은 잘못된 타입, 빈 값, 중복·반복 플래그(두 번째 값이 무시되거나 검증되지 않는가).
3. 다른 언어·형식(JS, SQL, 셸, desktop entry `Exec=` 줄, 템플릿, 정규식, JSON, XML)에 이어 붙이는 값은 그 형식의 인젝션 probe를 한다. 따옴표·이스케이프·줄바꿈·placeholder 문자열을 넣는다.
4. 여러 치환의 상호작용: 순차 `str.replace`나 템플릿에서 앞 치환의 결과가 뒤 치환의 placeholder가 되거나 문자열 리터럴을 벗어나는지 probe한다. 한 번의 구조적 인코딩(JSON 직렬화 후 한 번에 삽입)이 수정안이다.
5. 파싱 의미가 다른 두 소비자(예: D-Bus의 `Exec=` 파싱과 셸 word splitting)가 같은 값을 읽으면 두 쪽의 결과를 비교한다.

## 12. 반박 규칙과 `Considered`

- 후보는 반박으로만 버린다(PRR-50). 반박은 둘 중 하나다:
  - **probe**: §14 채널에서 실행한 probe. 결함 부류가 실제 프레임워크(MCP SDK, AnyIO, D-Bus, KWin 등)의 동작에 달렸으면 stub이 아니라 실제 프레임워크로 돌린다.
  - **argument+challenger**: 그 near-miss·인터리빙·경계·setup 타임아웃을 처리하는 정확한 줄을 인용한 코드 경로 논증. 독립 challenger 서브 에이전트에게 논증과 코드 위치만 주고 반례를 만들라고 지시한다(추론만, 실행 없음). challenger가 반례를 만들면 반박이 아니다.
- 논증은 후보와 같은 인터리빙을 다룬다. 두 임계 구역 사이(예: escalation 단계 사이의 대기, 락을 놓은 상태의 sleep·wait)에서 락이 풀리면, 그 틈에 다른 스레드나 프로세스가 같은 락으로 할 수 있는 일(reap, 등록, 삭제)을 하나씩 적는다. "검사와 실행은 원자적이다"는 단계 사이의 틈을 반박하지 못한다.
- challenger는 논증을 쓴 서브 에이전트가 아니어야 하고, 버리려는 바로 그 후보를 받아야 한다. `Considered` 항목에는 `argument+challenger(<agent name>)`로 그 challenger를 밝힌다. `<agent name>`은 spawn 도구가 돌려준 서브 에이전트 자신의 이름/id다. "independent reviewer", "challenger" 같은 일반 이름은 세지 않고, 그러면 그 항목은 반박이 아니다. challenger 자신의 답이 후보의 `file:line`을 인용할 때만 반박으로 센다. 그런 challenger의 답이 없으면 `argument+challenger`로 적지 않는다.
- 반박이 아닌 것: (a) 도구 문제로 probe가 실패했다, (b) "이를 일으키는 실제 입력이 알려지지 않았다"(하나 만들어 본다), (c) 사용자에게 보이는 출력이 거짓일 수 있는데 "그 자체로 계약 위반은 아니다", (d) near-miss probe나 challenger를 통과한 near-miss 논증 없이 불변조건을 단언한다. 유일성(정확히 하나만 일치), fail-closed 계약은 near-miss 사례(둘째 후보가 있지만 읽기 실패, 부분 열거)가 필요하다. (e) 코드 주석·docstring·이전 PR이 그 한계를 인정했다. 그것은 claim이다(PRR-07). PR이 더하거나 바꾼 경로에서 닿으면 finding이고, 아니면 기존 한계로 기록한다. (f) 명세가 없다·의도일 수 있다: 새·변경 파라미터·플래그·설정 키가 받아들인 값이 조용히 무시되거나 다른 값으로 바뀌면 명세가 없어도 결함이다. 기본은 P3이고, 사용자에게 보이는 출력이나 동작이 요청과 달라지면 P2다.
- 반박하지 못한 후보는 §8대로 등급을 매기고 PRR-49대로 처리한다.
- 버린 후보는 본문 끝의 접힌 섹션에 고정 형식으로 남긴다. 다음 head의 리뷰가 이 섹션을 파싱해 다시 본다:

  ```markdown
  <details><summary>Considered</summary>

  - [lens] <file:line> <hypothesis> — dismissed: <probe|argument+challenger(<agent name>)> <one line>

  </details>
  ```

  `[lens]`는 §10의 렌즈 이름이다. 보안 후보는 PR이 들여온 것(PRR-48)만 적는다. 기존 취약점은 PRR-19대로 어디에도 적지 않는다.

## 13. 저장소 관례 동기화

PRR-40의 방법이다. 저장소 지침은 자동으로 로드되지 않으므로 base 브랜치에서 직접 읽는다.

1. base 브랜치의 지침 파일 목록을 만든다: `git ls-tree -r --name-only origin/<base>`에서 AGENTS.md, CLAUDE.md, `.claude/**`, `.agents/**`, CONTRIBUTING*, `.github/pull_request_template*`, `.github/PULL_REQUEST_TEMPLATE/**`, `docs/`의 설계 문서, `.github/workflows/*`. `git show origin/<base>:<path>`로 원문 전체를 읽는다(PRR-39).
2. 워크플로는 실제로 실행하는 명령(lint, type check, 테스트 범위, PR 제목 검사)만 관례로 배운다. 그 실행 결과는 근거가 아니다(PRR-38). 저장소 merge 설정(`gh api repos/<owner>/<repo>`의 `allow_squash_merge`, `allow_merge_commit`, `allow_rebase_merge`, `squash_merge_commit_title`, `squash_merge_commit_message`)에서 어떤 텍스트가 기본 브랜치 커밋이 되는지(squash 제목의 출처가 PR 제목인지, 커밋 하나일 때 그 커밋 제목인지) 배우고, 그 텍스트가 관례를 따르는지 확인한다.
3. 동기화 트리거 체크리스트: 지침의 "X를 바꾸면 Y도" 규칙을 diff에 하나씩 적용한다(테스트 파일 목록, 도구 수, README 표, 문서 사이트, 변경 기록).
4. 낡은 산문 grep: 바뀐 심볼, 플래그, 기본값, 숫자, 동작 설명을 저장소 전체에서 grep해 이제 틀린 주석·문서·docstring을 찾는다.
5. 공유 카운터·레지스트리: 다른 열린 PR(`gh pr list --state open --json number,files`)이 같은 카운터나 목록을 바꾸면 둘 다 머지됐을 때의 값을 계산하고, 틀어지면 finding으로 적는다.
6. 관례 위반(PR 제목·커밋 메시지 형식, PR 템플릿 체크리스트, 금지된 억제)은 고친 텍스트(예: 제안할 PR 제목)를 담은 finding이다.
7. 적용한 파일과 base SHA를 `Verified`에 적는다. PR이 지침 파일을 바꾸면 그 변경은 리뷰 대상이고 지침으로 쓰지 않는다.

## 14. 격리 실행 채널

PRR-55 [U]의 방법이다. PR 코드(AST로 뽑은 함수, PR 모듈을 import하는 하네스, PR 스크립트, 테스트, 빌드·설치 도구)는 runner 호스트 셸에서 돌리지 않는다.

```sh
src=/tmp/issue-agent/<worktree-name>/src-<short-sha>
mkdir -p "$src" && git archive <head-sha> | tar -x -C "$src"
docker build -t review-<short-sha> -f <Dockerfile> "$src"   # no --allow; network only here
docker run --rm --network none -v "$src":/src:ro --tmpfs /tmp \
  -e PYTHONDONTWRITEBYTECODE=1 review-<short-sha> <command>
```

- `docker build`: `--allow` entitlement 없음. PR의 Dockerfile이나, 공식 베이스 이미지(`python:3.12-slim`, `golang:<ver>`, `node:<ver>` 등) 위에 에이전트가 쓴 scratch Dockerfile.
- `docker run`: 항상 `--rm --network none`. `--privileged`, `--cap-add`, `--security-opt` 완화, 호스트 네임스페이스 모드, docker 소켓 마운트, 홈 디렉터리 마운트, `--volumes-from`, bind 볼륨 드라이버 옵션은 쓰지 않는다. `-e`는 리터럴 상수만(`-e VAR`로 호스트 값 전달 금지, `--env-file` 금지). 장치는 필요할 때 `/dev/dri`, `/dev/dri/card0`, `/dev/dri/renderD128`만.
- worktree 디렉터리 자체는 마운트하지 않는다. `git archive` 사본이나 복사본을 `/tmp/issue-agent/<worktree-name>/` 아래에 두고 빌드 컨텍스트로 쓰거나 `:ro`로 마운트한다. 쓰기 가능한 캐시는 `--tmpfs`나 같은 scratch 아래 디렉터리.
- PR 자신의 docker 래퍼 스크립트(docker·compose를 부르는 스크립트)는 실행하지 않는다. 플래그를 읽어 위 규칙 안에서 재구성하고, 규칙이 막는 플래그(privileged Kind 등)가 필요하면 그 probe는 실행하지 않고 `Not verified`에 적는다.
- 호스트에서는 읽기, `git`, grep, 실행 없는 파싱만 한다. 컨테이너 안에서 할 수 없는 probe는 §12의 argument+challenger로 대신한다.
- 실행 후 컨테이너, 이미지, scratch 디렉터리를 정리한다.
