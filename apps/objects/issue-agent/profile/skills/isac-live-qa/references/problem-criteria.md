# 무엇을 문제로 볼 것인가

LQA-24, LQA-28~LQA-30의 세부. 인터뷰(항목 g)에서 사용자가 정한 기준이 우선한다. 태그 없는 항목은 바꿀 수 있는 기본값이다. 판정 dossier 형식(bug/intended/duplicate, 증거 등급)은 `issue-validation`이 소유한다.

## 1. 문제의 종류

| 종류 | 예 | 이슈 라벨 |
|---|---|---|
| 기능 결함 | 계약과 다른 동작, 잘못된 status, 정리되지 않는 원격 객체, 오래된 비밀값 | `bug` |
| 성능 결함 | reconcile 폭주, 불필요한 반복 쓰기, provider rate limit 대비 과도한 호출 | `bug` |
| UX 결함 | 설치 경로 실패, 오해를 부르는 오류 메시지, 문서와 다른 사용 절차 | `bug` |
| 설계상 낭비 | 이 배포가 쓰지 않는 대상을 스캔해 생기는 반복 오류·노이즈, 배포 규모에 비례하지 않는 작업 | `enhancement` |
| 개선 요청 | 로그에서 드러난 관측성 공백, 운영 부담을 줄이는 변경 | `enhancement` |

- 설계상 낭비는 LQA-29, 결함/개선 구분은 LQA-30, upstream 결함은 LQA-35.

## 2. 기본 coverage 후보

인터뷰 범위(항목 f) 안에서 대상 종류에 맞는 목록을 후보로 본다. 맞지 않는 항목은 뺀다.

### 예: Kubernetes 컨트롤러 배포

1. 모든 사용자 객체의 status·conditions·observedGeneration
2. 원격 상태와 클러스터 상태 대조(원격 설정 버전, 레코드 수, 연결 대상)
3. 인증 배선(토큰 audience ↔ 원격 설정)
4. 공개 경로에 실제 요청(로그인 redirect, 우회 경로, 라우팅되지 않은 경로의 응답)
5. 임시 namespace의 negative path(잘못된 참조, 누락 설정, 불일치 필드, 참조 변경, 권한 없는 namespace)
6. 선언 검증 규칙과 릴리스 샘플의 server-side dry-run
7. 종류별 삭제·finalizer 동작
8. 메트릭 비율(API 호출/s ↔ provider rate limit, requeue, 쓰기 양)
9. 시간 창 안의 resourceVersion churn
10. 데이터플레인 설정 dump
11. orphan 객체
12. 반복 오류 로그
13. 과거 재시작

### 웹 서비스·API

1. 주요 엔드포인트의 정상·오류 응답(상태 코드, 본문, 오류 메시지)
2. 인증 계약(무인증 / 잘못된 자격증명 / 정상 자격증명, LQA-25)
3. 주요 사용자 흐름의 end-to-end 결과
4. 서버·프록시 로그의 반복 오류와 느린 요청
5. 테스트 계정·테넌트에서 만든 데이터의 정리 경로

### CLI·데스크톱 앱

1. 안내된 설치 경로로 설치와 첫 실행(LQA-04)
2. 주요 사용자 흐름을 실제 입력 경로로 실행하고 화면·산출물로 확인
3. 오류 처리와 메시지
4. 크래시·로그 파일
5. 제거(uninstall)와 남는 파일

## 3. 증거 기준

- 문제 주장에는 관측된 live 증거나 결정적 재현이 필요하다. 반증 가능한 가설과 반사실·healthy control 비교를 쓴다.
- 이전의 "false positive" 판정도 사실이 아니라 가설로 다룬다.
- 관측과 모순되는 증상은 주장하지 않는다(예: 재시작 횟수 0인데 재시작 주장).
- 한계는 코드로 정량화하고, 이론상 시나리오와 실제 활성 구성을 분리한다.
- 조사자는 orchestrator의 가설을 믿지 않고 검증한다. 결론은 "진짜 버그지만 의심한 그 버그는 아님"일 수 있다. UID 변경, managedFields 같은 identity 확인을 증거에 넣는다.
- 표면 상태(Ready, Programmed 등)만으로 정상이라고 판정하지 않는다. 제어 루프 이상은 처리 시간 누계, 이벤트, churn 같은 별도 지표로 확인한다.

## 4. 측정 규칙

- 성능 문제는 측정한 뒤 판단한다. 수 분 간격으로 메트릭을 두 번 샘플링해 비율을 계산하고, 어떤 필드가 바뀌는지 watch로 관찰하며, provider rate limit과 문서화된 예산에 비교한다.
- 성능 주장에는 인상 대신 N회 측정 통계를 붙인다.
- live 환경에서는 벤치마크·부하 생성을 하지 않는다. 필요한 부하 측정은 격리 환경에서 한다.
- 부하로 생긴 timeout은 결과가 아니다. 직렬로 다시 측정한다.
- 대량 로그·메트릭은 컨텍스트에 원문으로 넣지 않는다. 저장소 밖 scratch에서 결정적 sanitize → template 정규화 → 반복 단위 집계(개수·시간 범위 보존)를 거치고, 집계 전후 합계를 맞춘다. 조용한 제외는 없어야 한다.
- 동종 항목이 20개 이상이면 눈으로 훑지 않고 결정적 도구로 분류한 뒤 표시된 것만 정독한다. subagent는 경로와 개수만 반환하고 판정은 받는 쪽이 한다.

## 5. 심각도

- 이론적 심각도가 아니라 현재 live 영향으로 매긴다(예: "이 환경의 대상 6개 중 5개 영향" → 높음).
- 요약 표에 심각도 열을 둔다. 척도는 높음/중간/낮음 기본, 프로젝트 문서가 있으면 그 척도를 쓴다.

## 6. 결과 등급

- 감사·리뷰형 산출물은 정확한 근거(file:line 또는 리소스 상태)가 있는 구체 결함만 심각도순으로 보고한다. 없으면 "GREEN / no findings"를 근거와 함께 명시한다. 증거 없는 제안은 뺀다.
- 결과는 "검증됨 / 추론 / 측정하지 않음"으로 구분한다. 측정하지 않은 보장을 주장하지 않는다.
- 커버리지 한계를 적는다: 로그 보존 구간, 이벤트 축약, 실행하지 못한 시나리오·조합, 정확한 trigger 경로 미규명.
