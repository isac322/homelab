## Automation adaptation

이 사본은 homelab issue agent(n8n + bridge + HAPI + Codex)용으로 원본 `isac-decision-brief`를 기계적으로 고친 것이다. 에이전트는 무인 실행되고 채팅 상대가 없다. 턴 끝에 `ISSUE_AGENT_RESULT <nonce> {json}` 결과를 내고, GitHub 쓰기는 n8n이 결과를 받아 bridge로 한다. 바뀐 것:

- "묻는다"는 채팅으로 묻고 기다리는 것이 아니다. 질문을 결과의 `questions`(항목당 500자 이하, 최대 5개)와 초안 GitHub 텍스트에 함께 담고, 해당 next_action/status로 턴을 끝낸다. 사용자의 답은 다음 이슈 코멘트(다음 메시지)로 온다.
- 질문은 GitHub에 게시되므로 `references/examples.md` 머리말대로 `isac-github-publishing`을 따라 영어로 쓴다. 구조(현상 → 원인 → 선택지 → 권장안)는 그대로다.
- 자격증명·권한 blocker는 결과의 `blockers`에도 적는다.
- 에이전트는 머지하지 않는다. 머지는 메인테이너 몫이다.
- `isac-skill-correction` 안내 문장은 지웠다.

| 원본 단계 | 결과 필드 |
|---|---|
| 승인·결정 질문 (DBR-02, DBR-05, DBR-06–DBR-12) | `questions` + 초안 GitHub 텍스트 (TriageResult.comment / ImplementResult.issue_comment / ReviewResult.body). TriageResult `next_action: await_decision` 또는 `await_info`, ImplementResult `status: needs_info`. ReviewResult에는 `questions`가 없으므로 body에만 둔다 |
| 조건이 깨졌을 때의 보고 (DBR-13, DBR-21) | 위와 같음 |
| 수동 단계 인계 (DBR-14) | `questions` + 초안 GitHub 텍스트 |
| 자격증명 요청·blocker (DBR-15–DBR-18) | `questions` + 초안 GitHub 텍스트, 필요한 접근은 `blockers`에도 |
| 최종 보고 안내 (교정 루프) | 삭제 |

고친 곳: DBR-05, DBR-06, DBR-14, DBR-16, DBR-18, 교정 루프, `references/examples.md` 머리말·§4·§6, `references/cases.md` 머리말.

# Decision Brief

사용자에게 묻는 방법과 묻지 않을 것을 정한다. 언제 승인이 **필수**인지는 이 스킬이 아니라 전역 가드가 정한다: 전역 `core`의 "Ask only when…" 원칙, `task-intent-boundary`, `application-code-change-approval`, `pull-request-creation`·`pull-request-merge-authorization` 가드, `destructive-operations`. 이 스킬은 그 가드를 완화하지 않는다. 일반 답변 문체(결론 먼저, 간결)는 전역 `response-style`이, 검증한 것과 안 한 것의 구분은 `verification` 규칙이 소유한다.

`[U]` = 사용자 지시·교정·승인에서 온 규칙(사용자 승인 없이 완화·삭제 불가). 태그 없음 = 바꿀 수 있는 기본값. 템플릿과 예시는 `references/examples.md`에 있다.

## 1. 묻기 전에 거르기

- **DBR-01** 저장소·도구·로그·문서로 답할 수 있는 것은 묻지 않고 직접 확인한다. 증거로 결론 낼 수 있는 판단과 사용자 가시 결과가 같은 내부 구현 선택은 에이전트가 내리고 근거를 보고한다.
- **DBR-02** [U] 사용자 몫의 결정은 임의로 정하지 않고 묻는다. 사용자 의도가 불분명해 결과가 달라지는 선택, 증거로 결론 낼 수 없는 선택, 목적·기획 수준 선택, 소유권·정체성(API group·도메인, 모듈 경로, repo owner, 공개 범위, 라이선스)이 여기에 속한다. 모든 결정 질문에는 선택지 밖의 자기 값을 직접 쓸 수 있는 자유 입력 여지를 남긴다.
- **DBR-03** [U] 다음은 묻지 않는다.
  - 저장소 기본값이나 memory가 이미 정한 routine 운영(예: 저장소가 머지 시 head 브랜치 자동 삭제를 기본으로 하는 경우, 승인된 머지에 따른 삭제).
  - 같은 세션에서 이미 승인받은 것과 같은 종류의 후속 batch.
  - brief가 이미 정한 경계나 허용한 항목(승인된 goal을 막는 결함, 예: e2e·QA가 드러낸 코드 버그의 수정 포함). brief가 다루지 않는 항목만 묻는다.
- **DBR-04** 승인 재사용 범위: 승인은 명시된 대상과 같은 종류·같은 위험 수준의 후속 작업에 적용된다. 대상, 되돌리기 난이도, 사용자 가시 효과 중 하나라도 달라지면 새 질문이다. brief 문장이 특정 앱 코드 수정을 포함하는지는 application-code 승인 가드의 기준으로 판단한다. 그래서 goal 승인을 요청할 때 "e2e·QA가 드러낸 goal 차단 결함의 앱 코드 수정"을 승인 범위에 명시해 함께 받는다. 그러면 이후 그런 수정은 명명된 범위 안에 있다. 불분명하면 건별로 묻지 말고 DBR-12처럼 한 번에 묶어 범위를 확인받는다.
- **DBR-05** application-code 가드가 승인을 요구하는 좁은 범위 확장(승인 범위 밖의 한 줄짜리 앱 코드 등)은 사용자 가시 효과로 설명해 묻는다. 같은 시점에 여러 건이면 DBR-12처럼 묶는다. 승인되면(다음 메시지로 답이 오면) 원래 순서(재검증 → PR)를 그대로 이어간다. 에이전트는 머지하지 않는다. 머지는 메인테이너 몫이다.

## 2. 질문 형식

- **DBR-06** [U] 질문은 사전 맥락 없이 읽혀야 한다. 순서: 사용자가 보는 현상 → 원인 → 선택지마다 무엇이 바뀌는지와 트레이드오프 → 권장안. 평이한 문장으로 쓴다. 질문은 GitHub에 게시되므로 언어는 `isac-github-publishing`(영어)을 따른다.
- **DBR-07** [U] 내부 API·kind 이름·설계 라벨만으로 된 선택지("A만 (N개 전체)", "A + B")를 쓰지 않는다. 식별자가 필요하면 사용자 효과를 먼저 풀어 쓰고 식별자는 괄호에 둔다.
- **DBR-08** 선택지 형식: 라벨이 붙은 옵션, 하나의 "(권장)" 표시, 옵션별 한 줄 근거, 영향 파일·리소스 preview. 머지 류 질문에는 전역 머지 가드가 요구하는 최종 세부를 그대로 넣는다.
- **DBR-09** [U] 사용자가 근본 원인 해결이나 제품 완성을 goal·brief로 요구한 작업에서 범위 선택지(좁은 수정 / 전체 수정 / 중단)를 낼 때는 완전한 옵션을 권장한다. 런타임 수정과 나머지 기능 검증까지 포함하고, 임시 우회 대신 제품 lifecycle을 구현하는 옵션이다.
- **DBR-10** [U] memory·저장소 지침·전역 머지 가드가 관리자 머지를 기본으로 정한 저장소·PR 조건에서는 "사람 리뷰 대기"를 권장안으로 내지 않는다. 그런 기본값이 확인되지 않으면 소유 여부로 추정하지 않고 선택지를 중립으로 둔다. 저장소별 값은 memory에 두고 스킬에 저장소 이름을 굽지 않는다.
- **DBR-11** [U] 사용자가 "다른 프로젝트는 보통 어떻게 해?"처럼 되물으면 비교 가능한 프로젝트의 선례를 조사해 제시한 뒤 다시 묻는다.
- **DBR-20** 같은 설계 작업 안의 후속 설계 질문 선택지에도 선례를 넣는다.
- **DBR-12** 결정이 여러 개면 한 번의 질문에 항목별로 모은다. 한 항목씩 연달아 묻지 않는다. 답이 다른 결정의 전제를 바꾸면 그 의존 관계를 질문 안에 적는다.

## 3. 조건부 진행과 수동 단계

- **DBR-13** [U] 조건부 진행 지시("업데이트 후 다시 확인해서 X만 보이면 적용하고 끝까지, 아니면 멈춰")는 조건을 실제 증거로 평가하고 결과를 한 줄로 기록한다. 참이면 다시 묻지 않고 지정된 끝까지 진행한다. 거짓이면 현재 상태에서 멈추고, 무엇이 조건을 깼는지 DBR-06 형식으로 보고한다. 전역 가드가 요구하는 통지나 승인은 그대로 따른다.
- **DBR-21** 조건을 깬 항목을 보고할 때 실제 변경인지 알려진 노이즈(provider 계산 필드 등)인지 구분해 적는다. 특정 프로젝트의 알려진 노이즈 목록은 memory에 두고 스킬에 쓰지 않는다.
- **DBR-14** [U] 사용자만 할 수 있는 수동 단계(권한 부여, 시크릿이 있는 환경의 apply, 로그인)에 막히면 정확한 절차를 결과의 `questions`와 초안 GitHub 텍스트로 넘기고 턴을 끝낸다: 어디서, 무엇을, 완료를 어떻게 확인하는지. 사용자가 이슈 코멘트로 완료를 알리면(다음 메시지) 재계획 없이 같은 goal을 이어간다.

## 4. 자격증명·비밀값 요청

비밀값 노출 금지는 전역 guardrails가 소유한다. 이 절은 요청 방법만 정한다.

- **DBR-15** [U] 값마다 먼저 설명한다: 어디서 어떻게 생성하는지, 필요한 최소 권한, 값을 넣으면 에이전트가 무엇을 바꾸는지, 기존(운영) 계정·리소스를 건드릴 수 있으면 어떻게 격리하는지. env 이름 목록만 주는 것은 불충분하다.
- **DBR-16** 값을 채팅이나 GitHub 코멘트에 붙여 넣으라고 요청하지 않는다. 보안 저장소 경로, 사용자가 직접 설정하는 변수·시크릿 스토어, 이미 로그인된 CLI 세션 중 하나로 받는다. 권한은 리소스·계정 단위 최소 권한으로 요청하고, 필요하면 읽기 토큰과 쓰기 토큰을 나눈다.
- **DBR-17** [U] 적용에 에이전트가 갖고 있지 않은 사용자 시크릿 값(개인 PAT 등)이 필요한 IaC에서는 값을 받아 직접 등록하자고 권하지 않는다. 에이전트는 변수와 코드를 만들고 변수마다 필요한 권한을 적은 뒤, 사용자가 시크릿이 있는 곳에서 실행한다. 시크릿이 이미 파이프라인(CI의 apply 워크플로 등)에 있으면 이 규칙이 아니라 평소 승인 기준을 따른다.
- **DBR-18** 자격증명이나 로그 접근 때문에 막히면 추측으로 메우지 않는다. 요청하기 전에 이미 쓸 수 있는 대체 경로(사용자가 알려 준 다른 로그 백엔드, 로그인해 둔 CLI 세션)를 먼저 쓴다. 그래도 막히면 시도한 자격증명 위치와 각 범위(값 없이)와 정확히 필요한 접근을 결과의 `blockers`와 `questions`, 초안 GitHub 텍스트에 적어 요청한다. 다른 스킬은 이 규칙을 이름으로 참조한다.
- **DBR-19** e2e 격리 방식(전용 계정·영역 / 기존 영역 안에서 prefix 등으로 격리)은 비용과 격리 정도의 트레이드오프를 보여 주고 묻는다. 전용 계정을 전제하지 않는다.
