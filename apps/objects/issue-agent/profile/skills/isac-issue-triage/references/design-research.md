# 구조 변경 방향 조사

근본 수정이 구조 변경을 요구할 때(SKILL.md TRI-25) 선택지를 만들고 비교하는 절차다. `isac-issue-to-pr` 스킬도 구현 중 구조·코어 변경이 필요해지면 이 절차를 쓴다. 결과는 `isac-decision-brief` 스킬 형식으로 결과의 `comment`와 `questions`에 담아 메인테이너 결정을 요청하고(`next_action: await_decision`), 승인 전에는 구현하지 않는다.

이 파일은 바꿀 수 있는 기본값이다. 사용자 지시에서 온 조사 원칙은 SKILL.md의 `[U]` 규칙(TRI-25, TRI-47, TRI-48)에 있다.

## 무엇이 구조 변경인가

공개 API, 스키마(CRD 등), 영속 상태, 소유권·단일 작성자 모델, 보안 불변식, 아키텍처 경계, 사용자가 소비하는 status·출력 계약을 바꾸는 수정이다. 내부 구현 선택만 다르면 구조 변경이 아니며 사용자에게 묻지 않는다. 프로젝트별 정의는 프로젝트 reference가 좁힐 수 있다.

## 원칙

- 조사 원칙은 SKILL.md TRI-47(실측·공식 문서·비교 모델링), TRI-48(항목당 호환성 분석)과 기본값 TRI-49(코드 재사용), TRI-50(불확실한 기술 기억 확인)이다.
- 조사 결과는 제품 표면을 이름으로 적는다: 어떤 벤더 기능을 쓰는지, 어떤 리소스·스키마 필드를 추가·변경하는지, 어떤 리소스에 어떤 annotation·참조를 두는지. 선례를 선택지에 붙이는 방식은 `isac-decision-brief` 스킬을 따른다.
- 토론 원칙(현상 유지 편향 금지, 사용자 제안 설계 반박과 대안 재탐색, 측정 없는 성능·우위 주장 금지와 `[INFERENCE]` 표시)은 `isac-multi-agent-consensus` 스킬을 따른다.
- 사용자가 X를 "다/전부" 지원하라고 했을 때의 범위(공식 API·스키마 전체 표면 parity)는 `isac-issue-to-pr` 스킬이 정한다. 이 절차는 아래 parity ledger로 그 목록을 만든다.
- 에이전트가 조사 중 범위를 넓혀 새 기능을 제안하지 않는다. 제안한다면 원래 목적과 분리해 적고, 사실상 별도 제품이 될 확장이면 먼저 그렇게 밝힌다.

## 절차

1. **Inventory.** 바뀔 필드, enum, 함수, 호출 경로를 file:line과 함께 빠짐없이 나열한다. 있다고 추측되는 기능은 present/absent로 확인해 적는다.
2. **Primary sources.** 공식 스펙·문서·SDK 스키마를 읽는다. 모든 주장에 URL과 "as of <date>" 기준일을 붙인다.
3. **Precedents.** 비교 대상 OSS 프로젝트마다 profile을 만든다: 리소스·annotation 목록, attach 방식, ownership·adoption·deletion 의미, 데이터 플레인, 이슈 트래커에서 드러난 한계, 라이선스. 그다음 교차 비교표와 관찰된 패턴·장단점을 쓴다.
4. **Empirical check.** 버전·설정·동작은 문서만 믿지 않고 실측한다(패키지 레지스트리의 실제 버전, 시그니처 확인, 일회용 컨테이너에서 바이너리 실행·validate·자원 측정). repo와 공유 환경은 건드리지 않는 scratch 영역에서만 한다. 결과는 verbatim 출력, 버전 표, 문서와의 차이 목록으로 남긴다.
5. **Options.** 선택지마다 바뀌는 것, 효과, 트레이드오프, 회귀 위험(현재 vs 제안의 사례별 비교), 남는 공백과 완화책, 필요한 테스트를 적는다. 기존 안전 불변식(fail-closed 인가, 소유권 검증, 삭제·해지 보존)을 약화시키는 선택지는 그 사실을 먼저 적는다.
6. **Verification of claims.** 채택 전에 두 번째 에이전트가 공식 소스로 주요 주장을 다시 확인한다.
7. **Brief.** `isac-decision-brief` 스킬 형식으로 `comment`·`questions`에 담는다. 사용자 관점에서 기존 대비 무엇이 달라지는지 구체적 예시(설정·리소스 YAML 등)로 보이고, 미검증 주장에는 `[INFERENCE]`를 붙인다.

## 보조 산출물

### 조사 보고서 계약(기본값)

- 번호 매긴 질문, 정확한 필드명과 URL, "as of <date>", 공식·1차 소스 우선.
- 필수 절: `## Findings`, `## Options`, `## Sources`, `## Open questions`.

### 다른 OSS 코드 재사용

- 복사 범위는 TRI-49.
- 패키지별 판정: `import` / `copy`(경로, LOC, 라이선스) / `reference only`. 채택하지 않은 근거도 남긴다.

### Parity ledger

공식 스키마·SDK와 현재 구현을 필드 단위로 비교한다(병렬 에이전트). 각 항목을 `mapped` / `excluded`(사유) / `actionable`로 두고 actionable이 0이 될 때까지 반복한다.

### 호환성 매트릭스

항목당 분석 에이전트 → 판정 정규화(arbiter) → 항목별 재검증 순서로 한다. 타입이 존재한다는 사실만으로 지원한다고 쓰지 않고 실제 처리 경로의 증거를 요구한다. 결과는 `FULL` / `PARTIAL` / `UNSUPPORTED` 매트릭스로 낸다.

## 범위 밖

- 의존성 버전 선택 정책 자체(최신 버전 사용·pin)는 이 절차가 정하지 않는다. 저장소 규칙이나 사용자 지시를 따른다.
- 조사 결과를 웹 페이지로 게시하는 일은 별도 요청이 있을 때만 한다.
