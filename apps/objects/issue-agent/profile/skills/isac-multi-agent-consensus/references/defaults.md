# 토론 프로토콜 기본값

이 파일의 내용은 바꿀 수 있는 기본값이다. 사용자 의무가 아니다. `[U]` 규칙은 SKILL.md에만 있고, 여기 내용으로 완화할 수 없다. 호출 스킬이 관점 목록이나 산출물 형식을 정하면 그것이 우선한다.

## 1. 관점 세트(MAC-09)

조사자 한 명에 관점 하나를 고정한다. 규모 게이트(MAC-05)가 사소로 판정하면 첫 관점 하나와 challenger만 쓴다.

| 용도 | 관점 |
|---|---|
| 근본 원인 | (1) 증상 코드 경로 (2) 상위 설계·계약·불변식·문서 (3) 구조적 한계와 같은 패턴의 형제 경로. 관점마다 file:line 근거가 있는 Five Whys를 쓴다(방법은 `five-whys-root-cause-analysis`). |
| 실제 문제인가 | (1) 계약·스펙상 의도된 동작인가 (2) 실제 관측 증거가 결함을 보이는가 (3) 환경·권한·테스트 도구 문제로 설명되는가. challenger는 "문제 아님" 쪽을 맡는다. |
| QA 목록 | 영향 반경을 관점별로 나눠 조사자에게 배정한다. 관점 목록은 호출 스킬이 준다. 조사자는 read-only로 "누락 항목 / 잘못된 기대값 / 동의"를 200단어 이내로 답한다. |
| 테스트 계층 | 항목마다 증명 가능한 가장 낮은 계층을 주장하는 쪽과, 순환 논증(가짜 구현이 우리 가정을 그대로 반영) 때문에 상위 계층이 필요하다는 쪽을 둔다. |
| 설계·구조 결정 | 입장별 advocate 1명씩, skeptic 1명. 현행안을 전제하지 않는 대안 advocate를 최소 1명 둔다(MAC-14). 합의 실패 시 arbiter. |
| 리뷰 | (1) 주장한 문제나 근본 원인을 실제로 해결하는가 (2) 회귀와 부작용 (3) 성능 (4) 테스트 유효성. 관련 있으면 보안을 추가한다. 호출 스킬의 리뷰 기준이 이보다 약할 수 없다. |

## 2. 역할별 반환 내용

- **조사자:** 판정 질문에 대한 결론 한 줄, 주장 목록(주장마다 근거 file:line 또는 관측 결과, 실행 여부), 미확인 사항.
- **advocate:** 가장 강한 논거, 예상 반박에 대한 답, `## Concessions`(상대 입장에서 인정하는 점).
- **challenger:** 주장별 수용/기각과 근거, 누락된 대안이나 반례.
- **arbiter:** 채택·기각 매트릭스(항목, 판정, 근거), 번복·철회 기록, 기각한 비현행 대안, 수용한 잔여 위험 표, 사용자 결정이 필요한 쟁점.
- 기각된 후보도 근거와 한계와 함께 남겨 같은 논쟁이 반복되지 않게 한다.
- **설계 반박(MAC-13):** 사실 정정 → 동의하는 부분 → 반박하는 부분(근거: 스펙·불변식·권한 경계) → 수정안 → 질문 순서로 쓴다.

## 3. 실행 격리와 권한

- 판정 리뷰어는 read-only다. 편집하지 않고 저장소에 쓰지 않는다.
- 재현·감사 실행자는 scratch 디렉터리, 컨테이너, 임시 namespace 같은 격리 환경에서만 실행한다.
- 조사자는 서로 격리되어 병렬로 동작한다. 같은 원격 계정이나 리소스를 바꾸는 작업만 직렬로 한다.
- 에이전트와 토론 역할은 GitHub에 쓰지 않는다. 게시는 n8n이 결과 필드를 받아 한다.

## 4. 심각도(MAC-19)

| 등급 | 의미 | blocking |
|---|---|---|
| `P0` | 데이터 손실, 보안 결함, 비밀 유출, 광범위 장애 | 예 |
| `P1` | 판정의 결론을 틀리게 하거나 산출물이 목적(주장한 문제 해결 등)을 달성하지 못하게 함, 회귀 | 예 |
| `P2` | 결함이지만 목적 달성은 유지되고 후속 처리 가능 | 아니오 |
| `P3` | 경미 | 아니오 |

PR이 대상이면 blocking은 "머지 전 필수 수정"이다. 실행하지 못해 막힌 항목(`blocked`)은 통과가 아니다. 판정에 따로 적는다. 우리 작업물의 종료 조건은 SKILL.md MAC-16이 정한다(`P2`도 0).

## 5. 라운드 상한과 종료

- 반박 라운드는 기본 2회다. 새 증거 없이 같은 논점이 반복되면 즉시 arbiter로 넘긴다.
- 계획·리뷰 게이트도 같은 상한을 쓴다. 사전 리뷰가 2라운드를 넘으면 남은 쟁점을 정리해 arbiter 판정이나 `isac-decision-brief` 형식의 결과 `questions`(ReviewResult면 body)로 넘기고 기다리지 않는다.
- 수정 → 재검증 루프(MAC-16)는 상한이 없다. 같은 finding이 2회 연속 닫히지 않으면 owner 교체나 접근 재검토를 arbiter가 정한다.

## 6. 사용자 보고 형식 (결과의 `summary`)

짧은 영어로, 결론을 먼저 쓴다.

1. 판정 한 줄(예: `GREEN`, `BLOCKING: P1 2건`, "실제 문제 3건 / 문제 아님 2건").
2. 채택·기각 요지: 항목마다 한 줄 근거.
3. 수용한 잔여 위험.
4. 사용자 결정이 필요한 쟁점: `isac-decision-brief` 형식으로 결과의 `questions`와 초안 GitHub 텍스트에 담는다.
5. 추론으로 남은 주장에는 `[INFERENCE]` 표시.
